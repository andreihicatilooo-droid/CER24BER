# CERBER V2 — база работы с запросами

Этот файл собран из актуальных материалов репозитория (`.github/copilot-instructions.md`, `.github/instructions/*.md`, `.github/skills/*`) как единая рабочая база для комфортной работы с любыми запросами.

## 1) Базовые правила взаимодействия

- Всегда вести диалог на русском.
- Любые user-facing тексты хранить централизованно в `src/cerber_bot/texts.py`.
- Для сырой идеи сначала делать brief (ядро, сигнал, ограничения, направления, рекомендация, следующий агент), а не сразу писать код.
- Для уже согласованного плана перенос в TODO делать через контур `plan-to-todo`.

## 2) Карта ролей (агентов) для маршрутизации

- **CERBER (универсальный вход)** — если запрос размытый и нужно определить правильный режим работы.
- **Discovery** — если есть только идея/ощущение проблемы и нужно сформировать направления.
- **Planner** — если нужно разложить задачу на этапы, зависимости и риски.
- **Architect** — если нужно сравнить варианты реализации и принять архитектурный компромисс.
- **Interface** — если меняются UX-flow, кнопки, тексты, шаблоны.
- **Cleanup** — если нужен аудит хвостов: dead code, дубли, устаревшие TODO/артефакты.
- **Executor** — если задача уже определена и нужно реализовать её end-to-end.
- **Router** — если непонятно, кого из агентов вызывать первым.

## 3) Промпт-шаблоны под частые запросы

### Сырая идея
`Собери brief по идее: <описание>. Нужны 2–4 направления, риски и рекомендуемый следующий агент.`

### Планирование
`Разложи задачу на этапы с зависимостями, рисками и критериями готовности: <задача>.`

### Архитектурный выбор
`Сравни 2–3 варианта реализации для <контекст>, укажи компромиссы и рекомендуй вариант.`

### Реализация
`Возьми следующую задачу из TODO и реализуй минимальными изменениями: <контекст>.`

### UI/тексты
`Предложи улучшение UX и текстов для <экран/flow>, без архитектурного redesign.`

### Cleanup
`Проведи cleanup-срез по <модуль/папка>: dead code, дубли, stale TODO, orphan files.`

## 4) Обязательные repo-правила (из инструкций)

### `.env.example` ↔ `launcher.py`

При добавлении/удалении/переименовании env-переменных синхронизировать:
- `.env.example`
- `launcher.py` (`ENV_SECTIONS`)

### Интеграции внешних API

Перед изменениями в интеграциях читать `doc/api/README.md` и профильный hint:
- NicePay → `doc/api/nicepayapi.md`
- GiftAPI → `doc/api/giftapi-hint.md`

Правила:
- HTTP-логика в `integrations/`, бизнес-логика в `services/`
- HMAC-сравнение через `hmac.compare_digest()`
- секреты не логировать и не коммитить

## 5) Комфортный цикл работы по запросу

1. Кратко уточнить цель и критерий готовности (если неясно).
2. Выбрать роль/агента по карте выше.
3. Если это идея — сначала brief, потом план.
4. Если это код — минимальные точечные правки + проверка.
5. По итогам — короткая сводка: что сделано, что осталось, какие риски.

## 6) Быстрый чеклист качества ответа

- [ ] Ответ на русском и без лишней воды  
- [ ] Выбран корректный агент/режим  
- [ ] Учитываются ограничения репозитория  
- [ ] Нет выдуманных возможностей/инструментов  
- [ ] Следующий шаг понятен пользователю
